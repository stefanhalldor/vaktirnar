## Spurning 1: Function grants, RLS og Storage policies

**Niðurstaða: Rétt afmarkað.**

- `ENABLE ROW LEVEL SECURITY` + `REVOKE ALL FROM PUBLIC, anon, authenticated` +
  `GRANT ... TO service_role` á töflunni er rétt mynstur.
- Báðar functions nota `SECURITY INVOKER` með `SET search_path = public`. Þetta
  er öruggara en `SECURITY DEFINER` og rétt þar sem aðeins service_role hefur
  EXECUTE réttindi.
- Storage bucket: `public = false` + engar `storage.objects` policies. service_role
  nær í gögn gegnum Storage API án policy. anon/authenticated geta ekki komist að
  gögnum, hvort sem RLS er á eða ekki.

Ekkert athugavert.

## Spurning 2: Update-then-upload-then-ready crash safety

**Niðurstaða: Öll þrjú crash-gluggar eru meðhöndluð rétt.**

| Gluggi | Staða eftir crash | Cleanup |
|--------|------------------|---------|
| Eftir path-register, fyrir upload | row: `building` + `storage_path` skráð, engin Storage object | Lease rennur út (20 mín) → `failed` → `failRoadGraphSnapshot` les `storage_path` og kallar `remove`. Object er ekki til; Supabase `remove` á tómt er no-op. |
| Eftir upload, áður en `ready` UPDATE | row: `building`, Storage object til | Sama lease-path → `failRoadGraphSnapshot` nær í `storage_path` og eyðir object. |
| `status=ready` UPDATE misheppnast (line 213) | Object til, row enn `building` | Inline cleanup (línur 213-214) eyðir object strax. `failRoadGraphSnapshot` í catch-blokk keyrir svo aftur — duplicate `remove` er no-op. |

Athugasemd um `pruneRoadGraphSnapshotHistory`: Storage delete kemur á undan
metadata delete. Ef Storage delete bilar er skilað `return`/`continue` og
metadata-röðin lifir þar til næsta prune. Þetta er rétt hegðun — metadata-rofinn
tapast ekki og next prune reynir aftur. Gagnstæð röð (delete metadata first)
myndi valda orphan Storage objects sem eru ekki rekjanlegir.

## Spurning 3: Rollback með promotion á retained retired snapshot

**Niðurstaða: Fullnægjandi og atomic.**

`promote_teskeid_road_graph_snapshot` notar:

1. `pg_advisory_xact_lock` — tryggir að aðeins einn promotion keyri samtímis.
2. `SELECT ... FOR UPDATE` á target-röðina — læsir hana innan færslunnar.
3. Bæði UPDATE (old `active` → `retired` og target → `active`) eru í sömu
   PostgreSQL-færslu.
4. `UNIQUE INDEX WHERE status = 'active'` kemur í veg fyrir tvær active raðir.
   MVCC tryggir að millibil innan færslunnar sjáist ekki öðrum transactions.

Rollback-flæðið er: `promote_teskeid_road_graph_snapshot(<retained-retired-id>)`
skilar retired snapshot í `active` og setur núverandi active í `retired` atomically.
Þetta er fullnægjandi.

## Spurning 4: 20 mín lease, 50 MiB compressed, 100 MiB uncompressed

**Niðurstaða: Mörkin eru raunhæf og rúmleg.**

- **20 mín lease**: Vercel function max er 300 sek (5 mín). Yfirgefin process
  losnar þess vegna alltaf löngu áður en 20 mínútur líða. Mörkin vernda gegn
  deyðum processes án þess að vera of þröng.
- **100 MiB uncompressed**: 1,200+ Vegagerðarsegment með geometry eru líklega
  5-15 MiB óþjöppuð JSON. Mörkin eru mjög rúmleg.
- **50 MiB compressed**: gzip level 9 á JSON gefur venjulega 5-10x þjöppun.
  Raunleg compressed stærð er líklega 1-3 MiB. Mörkin eru mjög rúmleg.

Eina óvissan er raunveruleg payload-stærð sem þarf bootstrap til að mæla. Þetta
er þekkt óvissa sem Codex skráir og er ekki release-blocker.

## Spurning 5: Fimm mínútna warm LKG retry-backoff

**Niðurstaða: Réttur tradeoff.**

`ACTIVE_VERSION_RECHECK_MS = 5 * 60 * 1000` (5 mínútur).

- Vegagrunn breytist sjaldan (dagleg refresh). 5 mínútna seinkun á að taka í
  gildi nýtt snapshot er alveg viðunandi.
- Ef metadata-lestur bilar: `cached.lastVersionCheckAt = Date.now()` er sett
  (roadGraphRuntime.server.ts lína 98). Næsti raunverulegi tilraun er þ.a.l.
  5 mínútum seinna — þetta kemur í veg fyrir hammerning á Supabase ef endpoint
  er tímabundið niðri.
- `pending` deduplication er process-global (`let pending`). Í serverless eru
  cold-starts einangraðir processes; concurrent requests innan sama process
  deila `pending` promise rétt.

## Spurning til Codex: pruneRoadGraphSnapshotHistory og `failed` rows

`failed` og `unchanged` rows eiga venjulega ekki Storage object (þær fara aldrei
í gegnum `stageRoadGraphSnapshot`). Undantekningin er ef process deyr á milli
path-register og upload — en þá tekur lease-expiry og `failRoadGraphSnapshot`
þegar um sig.

Þegar prune-fallið leitaðar að Storage paths á `failed`/`unchanged` rows (línur
296-311) eru þær paths venjulega `null` og filter-ið útilokar þær rétt. Þetta
virðist rétt en Codex má staðfesta að engin `failed` row geti haft lifandi
Storage object sem prune-fallið mætti missa.
